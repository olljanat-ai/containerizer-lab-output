Generated by containerizer for GitHub Actions. It builds the application's components from this repository with the Dockerfiles the assessment generated, scans them and pushes them to the registry the generated Kubernetes manifests use.

## What it does

- Pull/merge requests: build, SBOM (Syft, CycloneDX JSON, kept as an artifact) and vulnerability scan (Trivy: fails on CRITICAL, fixable ones only). Nothing is pushed.
- Default branch: the same, then push and tag `1.<yyyymmdd>.<hhmm>` (UTC) and `sha-<commit>`.

The build context is `scenarios/expense-claims` (the application's folder). `Dockerfile.dockerignore` next to each Dockerfile is the context filter (BuildKit reads `<Dockerfile>.dockerignore`), so the repository's own `.dockerignore`, if any, does not apply. Build locally the same way:

```sh
DOCKER_BUILDKIT=1 docker build -f scenarios/expense-claims/containerizer/<component>/Dockerfile scenarios/expense-claims
```

## Set up

1. Images go to GitHub Container Registry (`ghcr.io/<owner>`) with the workflow's `GITHUB_TOKEN`: nothing to set up. After the first push, link each package to the repository (package settings) so the token keeps write access, and make it public or give the cluster a pull secret.
2. Optional repository variables: `CONTAINERIZER_REGISTRY` (another registry and path, e.g. `registry.example.com/team`), `CONTAINERIZER_TRIVY_SEVERITY` (e.g. `HIGH,CRITICAL`), `CONTAINERIZER_TRIVY_IGNORE_UNFIXED`, `CONTAINERIZER_PUSH_LATEST=true`.
3. Pushes to the default branch publish only if Actions may run (Settings → Actions → General); protect the branch so only reviewed changes publish images.

## The GitOps sandbox

The generated Flux image automation (`gitops/flux/git/image-automation.yaml`) follows the newest semver tag `>=1.0.0` of each image and writes it to the `kustomization.yaml` of the output repository. The tags this pipeline pushes are that scheme (the same as the containerizer scans), so a push to the default branch reaches the sandbox without another step, as long as both use the same registry.

## Pins

Scanner images are pinned by version and digest, GitHub actions by commit SHA (the tag in the comment), cosign by its release checksum. Update them by generating the pipeline again with a newer containerizer (`containerizer pipeline`), or by hand: `docker buildx imagetools inspect <image>:<tag>` for a digest, `git ls-remote https://github.com/<action> refs/tags/<tag>` for an action.
